# Storage & Telemetry Setup

What changed, how to finish the setup, and how to verify each piece.

---

## 1. Architecture after this change

| Data | Where it lives | Why |
|---|---|---|
| Auth (users, sessions, tokens) | **Firebase Auth** | Only Firebase can do this |
| Premium entitlement (`Users/{uid}`) | **Firestore** | Written *only* by the `consumeFreeTrip` / `verifyPurchase` Cloud Functions via the Admin SDK, so a client can't forge `premium: true` |
| Trips (all tiers) | **SQLite** `trips` | One table replaces four parallel stores |
| Free-trip counter (local mirror) | **SQLite** `user_stats` | Instant + offline gating; server copy stays authoritative |
| Place photo / weather caches | **SQLite** `kv` | TTL enforced in SQL |
| Analytics events | **SQLite** `analytics_queue` → GA4 | Durable buffer, survives offline |
| Crash / error log | **SQLite** `error_log` → Crashlytics | Local mirror makes it testable |

Firestore is now imported in exactly two places: `hooks/useBilling.ts` (entitlement listener) and `services/db/migrateLegacy.ts` (one-time import of old trips).

### Files added

```
services/db/index.ts            open + migrate + health check
services/db/schema.ts           the SQL, versioned via PRAGMA user_version
services/db/trips.ts            trip repository + free-trip counter
services/db/kv.ts               expiring key/value cache
services/db/migrateLegacy.ts    one-time AsyncStorage + Firestore import
services/telemetry/index.ts     initTelemetry, identifyUser, status, self-test
services/telemetry/analytics.ts queue + native/GA4 backends
services/telemetry/crash.ts     error log + global handlers + test crash
services/telemetry/events.ts    event name catalogue
services/telemetry/config.ts    dev gating
services/telemetry/nativeFirebase.ts  optional @react-native-firebase bridge
services/diagnostics/apiKeys.ts on-device API key checks
app/diagnostics.tsx             Diagnostics screen (dev builds, via Profile)
scripts/test-api-keys.mjs       npm run test:keys
scripts/test-sqlite-schema.mjs  npm run test:db
```

## 2. First run

```bash
npm install            # picks up expo-sqlite
npm run test:db        # 22 SQL assertions, no device needed
npm run test:keys      # live request per API key
npx expo start -c      # -c clears the Metro cache
```

Run `npx expo start -c` **before** `npm run typecheck`. `typedRoutes` is on, and the route union in `.expo/types/router.d.ts` is generated by Metro — until it regenerates, `router.push("/diagnostics")` in `app/(tabs)/profile.tsx` reports a false type error because the new screen isn't in the union yet.

Nothing else is required — SQLite creates and migrates `avent.db` on first launch, and existing trips are imported automatically the first time MyTrips opens.

### Migration safety

`services/db/migrateLegacy.ts` imports from both legacy sources on first launch:

- AsyncStorage: demo trips, free-tier trips **and their free-trip counters**, the pending-sync queue, and the Firestore read-through cache.
- Firestore `UserTrips`, once per account.

Three properties worth knowing:

- **Legacy keys are not deleted.** A bug here is recoverable rather than destructive. They're small; clean them up in a later release once you're confident.
- **A source is only flagged done after a clean pass.** A partial import retries next launch instead of silently losing the rest.
- **Free-tier trips keep the uid from their own storage key**, not the currently signed-in uid — otherwise account A would inherit account B's trips on a shared device.

## 3. Analytics & Crashlytics

Two facts drive the design here:

- `firebase/analytics` (JS SDK) is **browser-only**. It needs `window` and the gtag script, so it cannot work in React Native.
- **Crashlytics has no JS SDK at all.** It is native-only by design — it has to catch native crashes before any JS runs.

So `services/telemetry/*` picks a backend at runtime instead of at build time. No code changes are needed to move between the two modes.

### Mode A — works today, in Expo Go

- **Analytics:** GA4 Measurement Protocol over `fetch`.
- **Crashes:** JS errors caught by `ErrorUtils` + unhandled promise rejections, written to `error_log`.
- **Limits:** no Crashlytics dashboard, and native crashes (a bad native module, OOM) are invisible.

To turn on the GA4 path:

1. GA4 Admin → Data Streams → your stream → **Measurement Protocol API secrets** → Create.
2. Put it in `.env`:
   ```
   EXPO_PUBLIC_GA4_API_SECRET=your_secret
   EXPO_PUBLIC_FORCE_TELEMETRY_IN_DEV=true
   ```
3. Restart Metro, open **Profile → Diagnostics → Send test event**.

`EXPO_PUBLIC_FORCE_TELEMETRY_IN_DEV` exists because reporting is off in `__DEV__` by default — otherwise every Fast Refresh red-screen lands in the same dashboard as your real users. Set it back to `false` when you're done.

### Mode B — real Firebase Analytics + Crashlytics (needs a dev build)

```bash
npx expo install @react-native-firebase/app \
                 @react-native-firebase/analytics \
                 @react-native-firebase/crashlytics
```

Download the config files from the Firebase console and put them in the project root:

- **Android:** Project Settings → Your apps → Android app (`com.Tripplanner.company`) → `google-services.json`
- **iOS:** the iOS app → `GoogleService-Info.plist`

You will need to *register* an Android app in the Firebase project first — right now only a Web app exists, which is why the JS SDK works but native does not.

Then in `app.json`:

```json
{
  "expo": {
    "android": { "googleServicesFile": "./google-services.json" },
    "ios": { "googleServicesFile": "./GoogleService-Info.plist" },
    "plugins": [
      "expo-router",
      "expo-iap",
      "@react-native-firebase/app",
      "@react-native-firebase/crashlytics",
      ["expo-build-properties", { "ios": { "useFrameworks": "static" } }]
    ]
  }
}
```

`expo-build-properties` with `useFrameworks: static` is required by the Firebase iOS SDK; skip it and the iOS build fails at pod install.

```bash
npx expo install expo-build-properties
eas build --profile development --platform android
```

Once installed, `services/telemetry/nativeFirebase.ts` finds the modules and every `logEvent` / `recordError` call automatically routes to real Firebase. `EXPO_PUBLIC_GA4_API_SECRET` is then unnecessary.

**Expo Go will no longer run the app after this step** — native modules require a dev build. Keep a `demo`/Expo Go branch if you still need quick previews.

### Verifying Crashlytics end to end

1. **Profile → Diagnostics → Send non-fatal error.** Appears in Crashlytics within a few minutes, under *Non-fatals*.
2. **Send test crash.** Force-closes the app. **Reopen the app** — Crashlytics uploads reports on the *next* launch, not at crash time. This confuses everyone the first time.
3. Debug-mode analytics on Android:
   ```bash
   adb shell setprop debug.firebase.analytics.app com.Tripplanner.company
   ```
   Events then show up live in Firebase → Analytics → DebugView.

## 4. Instrumented events

`services/telemetry/events.ts` is the single catalogue. GA4's reserved names (`login`, `sign_up`, `purchase`, `screen_view`) are used where they apply so the built-in reports populate.

Wired up so far:

- **Auth:** `sign_up`, `login`, `logout`, `auth_error` (with the Firebase error code)
- **Trip funnel:** `trip_flow_start`, `trip_generate_start`, `trip_generate_success` (with duration), `trip_generate_failed` (with reason), `trip_saved`
- **Monetisation:** `paywall_view` (with source), `paywall_dismiss`, `purchase_start`, `purchase`, `purchase_failed`, `purchase_restored`
- **Screens:** `screen_view` on SignIn, SignUp, MyTrips, Profile

`purchase` fires only *after* server-side verification succeeds, so revenue numbers can't be inflated by spoofed client purchases.

No PII is sent. Only `uid` goes to Analytics/Crashlytics — never the email — because GA4 and Crashlytics both prohibit it. Purchase tokens never leave `useBilling` / `verifyPurchase`.

One caveat inherent to Mode A: `EXPO_PUBLIC_GA4_API_SECRET` is inlined into the JS bundle, so it's extractable from a shipped APK and anyone holding it can write events into your GA4 property. That's unavoidable for client-side Measurement Protocol. It's fine for testing and for a soft launch; move to Mode B before it matters.

## 4b. Billing bypass (test mode)

> **`EXPO_PUBLIC_BILLING_BYPASS` is currently `true` in `.env`.** Set it to `false` before any production build, or every user gets premium for free.

While real billing isn't set up yet, tapping any plan on the paywall grants premium immediately — no Google Play sheet, no purchase token, no `verifyPurchase` Cloud Function.

**How to use it**

1. Sign in (the entitlement is per-account, keyed on uid).
2. Profile → Avent Premium, or any paywall → tap **Monthly** or **Yearly**.
3. Premium is granted and written to SQLite. Restart the app — it's still there.
4. To go back: **Profile → Diagnostics → Reset to free tier**. Removes the grant and sets the free-trip counter to 0, so the paywall and the "you've used your free AI trip" limit can both be retested. Saved trips are kept.

**How it behaves**

The grant produces the same `UserEntitlement` shape the Firestore listener does, so no screen has a test-mode special case — `PremiumGate`, the trip limit, the premium screen's status card and purchase history all render exactly as they will for a real subscriber. Monthly gets a 30-day expiry, yearly 365 days, and the order ID is prefixed `TEST-` so a test purchase is recognisable wherever it surfaces.

Two things the bypass has to override, which is where the subtlety is:

- **The Firestore listener is skipped while a grant exists.** Firestore knows nothing about the grant, so its `premium: false` would revoke it on the very next snapshot.
- **Reset clears the server-entitlement cache too.** That cache (added so premium survives being offline) would otherwise hydrate premium straight back on the next sign-in, making the reset look broken.

**Three guards against shipping it**

1. Inert unless the env var is exactly `"true"` — anything else and the real expo-iap path runs untouched.
2. A loud console warning on every app launch.
3. A yellow **TEST MODE — no real payment** banner on the premium screen and on every paywall modal.

Analytics `purchase` events from a bypass grant carry `test_mode: true`, so they can be filtered out of GA4 revenue.

**Going live later:** set the flag to `false`. Nothing needs deleting — `services/billing/localEntitlement.ts` becomes dead weight and the expo-iap + Cloud Function path takes over. Existing test grants stay in SQLite but are ignored, since the bypass check runs before the read. Follow `BILLING_SETUP.md` for the Play Console side.

**Note on Expo Go:** `RealBillingProvider` calls expo-iap's `useIAP()`, which is a native module. If you're testing in Expo Go rather than a dev build, set `EXPO_PUBLIC_DEMO_MODE=true` — the bypass works identically in the demo provider.

## 4a. Other fixes made while wiring this up

These were found while reviewing the migration and were fixed in the same pass:

- **A failed generation no longer burns a free trip.** The credit is consumed before the Gemini call (so a deep link into `generate-trip` can't bypass the gate), but the Gemini-failure and save-failure paths now call `refundFreeTrip()`. Previously two transient network errors could silently consume a user's entire free tier. The refund clamps at zero, so a double refund can't mint credits.
- **Premium status survives being offline.** The verified entitlement is now mirrored into the SQLite `kv` table after every snapshot and read back at sign-in. Before, `premium` existed only in memory and only arrived via a Firestore `onSnapshot` — so a paying user opening the app offline was treated as free tier, gated behind the paywall, and charged free-trip credits. The cache is only a seed; the next snapshot overwrites it.
- **MyTrips subscribes to auth state** instead of reading `auth.currentUser` once. Firebase restores the persisted session asynchronously, so on a cold start straight into that tab the old code saw `null` and showed an empty trip list with nothing to trigger a re-render.
- **`migrateLegacyData` shares one in-flight run.** Both a mount effect and a focus effect used to call it on first render, so AsyncStorage was drained twice and the Firestore query ran twice.
- **A failed SQLite migration now rejects** rather than returning a handle with no tables — which had turned one clear startup error into scattered "no such table" unhandled rejections. `PRAGMA user_version` is also bumped inside each migration's transaction, so a kill mid-migration can't leave committed work that re-runs.
- **The analytics queue is bounded by total rows**, not just sent rows. In dev — and in any build with no backend configured — nothing is ever marked sent, so the old prune deleted nothing and the table grew without limit.
- **GA4 is validated once at startup.** `/mp/collect` returns 204 even for a wrong measurement id or bad secret, so events used to be marked delivered while GA4 discarded them. The debug endpoint is now checked once and the backend is treated as unconfigured if it fails.

Found during the billing-bypass review and fixed in the same pass:

- **`consumeFreeTrip` checks `premium` before the demo branch.** Demo mode has its own free-trip gate reading a separate AsyncStorage entitlement, so a premium user in a demo build was still refused after two trips and bounced to the paywall.
- **Premium can't leak between accounts on a shared device.** Unsubscribing a Firestore listener doesn't stop an *already executing* async callback, so account A's callback could resume after sign-out and write A's entitlement back into the store — which B then inherited until B's own first snapshot (i.e. the whole session, if offline). The callback now re-checks `auth.currentUser` before writing, and the cache hydration explicitly resets to the free-tier shape when there's nothing cached.
- **`generate-trip` waits for `entitlementLoaded`.** On a cold start `premium` is still false for a moment, so a paying user opening that screen directly would burn a free-trip credit — and at the limit, see the paywall. There's a 6-second fallback so the screen can't spin forever, and a ref so it can only fire once.
- **The bypass purchase/restore paths are guarded.** They set `purchaseState` to `purchasing`/`verifying` first; an unguarded SQLite failure would have left `busy` true forever, disabling every plan button for the rest of the session.


Confirm the fix: `npm run test:keys` should report *"unauthenticated reads correctly denied"*. Before deploying, diff `firestore.rules` against what's live in the console.

This matters less than it did — trips are in SQLite now — but the `Users` entitlement collection is still there, and any trips already written to Firestore remain readable by anyone holding the API key, which is shipped inside the app bundle.

## 6. Verification checklist

```bash
npx expo start -c        # first: regenerates .expo/types/router.d.ts
npm run test:db          # 22 SQL assertions: schema, upserts, ordering, refunds, queue trim
npm run test:keys        # live API key requests
npm run typecheck        # tsc --noEmit
```

`npm run test:db` runs the app's real SQL against Node 22's built-in `node:sqlite`, reading the migrations straight out of `services/db/schema.ts` so it can't drift from what ships. It catches typo'd columns, wrong placeholder counts and broken `ON CONFLICT` clauses — the bugs that otherwise only appear as a crash on a phone.

On a device, **Profile → Diagnostics**:

- [ ] Database open & writable, schema v1, 6 tables
- [ ] Trips stored — count matches what MyTrips shows
- [ ] Reporting enabled (needs `EXPO_PUBLIC_FORCE_TELEMETRY_IN_DEV=true` in dev)
- [ ] Send test event → reports which path delivered it
- [ ] Send non-fatal error → appears in the local log, and in Crashlytics on a dev build
- [ ] Run API key checks → all green
- [ ] Generate a trip, force-quit the app, reopen → trip still there (proves SQLite persistence, not just in-memory state)
- [ ] Turn on airplane mode, generate a trip → saves with no error and no "pending sync" state

Billing bypass (while `EXPO_PUBLIC_BILLING_BYPASS=true`):

- [ ] Paywall shows the yellow **TEST MODE** banner
- [ ] Tap a plan → premium granted, status card shows the plan and a `TEST-` order ID
- [ ] Force-quit and reopen → still premium
- [ ] Premium features unlock (Discover, weather, packing, unlimited trips)
- [ ] Diagnostics → **Reset to free tier** → back to free, free trips 0 of 2
- [ ] Reopen the app after resetting → still free (i.e. premium didn't come back from cache)
- [ ] Generate 2 trips as a free user → the 3rd hits the paywall
